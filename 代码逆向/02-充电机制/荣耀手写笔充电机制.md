# 荣耀手写笔充电机制（代码级分析）

> 分析对象：`com.hihonor.hnbluetoothpencilmanager` **11.0.0.7**（工作区 `xgu4pv6j`）
> 方法：逐方法读 smali；结论均标注类/方法/行号。
> 目标问题：**现有代码能不能做到“磁吸之后，电量 90% 以上就不充电”？**

---

## 0. 结论速览

| 问题 | 结论 |
|---|---|
| 代码里有没有“按笔电量阈值启停充电”的逻辑？ | ❌ **没有**。全包搜不到任何“读笔电量 → 与阈值比较 → 开关充电”的路径 |
| 反向无线充电的开关代码在哪？ | `HwKeyboardController` 里有常量 `CHARGE_PATH = "sys/class/hw_power/charger/wireless_tx/tx_open"` 与 `START/STOP_REVERSE_CHARGING`，但**只声明、无引用（死代码）** |
| 那“充不充电”由谁决定？ | **键盘/笔里的充电 IC + 内核充电策略**；应用只是“上报状态 + 转发广播 + 回答宿主的充电状态” |
| 应用层唯一能碰到的“决策点”是什么？ | 键盘会**查询“宿主（平板/键盘）是否在充电”**，应用把 `mHostChargingState` 回发给它 —— 这才是“笔只在键盘充电时才充”的落点 |
| 所以能不能现在做到“≥90% 停充”？ | **不能。** 见第 3 节（三条原因） |

## 1. 充电链路总览

```
【供电侧】平板/键盘机身线圈  +  键盘或笔内的充电 IC
        ↑ 反向无线充电开关（硬件/内核）
        │  可写节点（本版未被引用）：sys/class/hw_power/charger/wireless_tx/tx_open
        │
【键盘固件】决定“要不要给笔供电/充电”的**真正策略方**
        │  ① 下发命令  com.honor.bluetooth.extra.CHARGING_CMD（cmd id: 1/2/4/5/8）
        │  ② 查询宿主充电状态（cmd id = 4）→ 等应用回答
        │  ③ 上报“开始反向充电”（HPP 报文）
        ▼
【本应用 com.hihonor.hnbluetoothpencilmanager 11.0.0.7】
  HwKeyboardController：
    · onGetChargingCmdFromKeyboard()  命令分发
    · onGetChargingStateInqEvent()     把 mHostChargingState 回发给键盘  ← 唯一“决策相关”输出
    · onGetStartReverseCharging()      只转发广播 KEYBOARD_CHARGING_CHANGED
    · HidInterface.isCharging()        反射 BatteryManager.isChargingEx() 读宿主是否充电
  HwPencilController：
    · onGetChargingState()             读笔上报的充电状态 → 写 honor_bt_pencil_charging_state
        │
        ▼
【设置键 / UI】
  honor_bt_pencil_charging_state ("0"/"1")
  honor_bt_pencil_battery_level
  悬浮菜单里的电量显示 / 低电量弹窗
```

**一句话**：应用是“**翻译官 + 上报员**”，不是“充电开关”。

## 3. 为什么现在做不到“≥90% 就不充电”

| # | 原因 | 依据 |
|---|---|---|
| 1 | **应用层没有“读笔电量 → 比较阈值 → 控制充电”的代码** | 全包只有 `checkLowBattery` 的 10/5/2 弹窗；无任何充电开关逻辑 |
| 2 | **反向充电的写开关是死代码**（即使活着也是 sysfs 内核节点，非应用职责） | `CHARGE_PATH`/`tx_open`/`START_REVERSE_CHARGING` 均只声明未被引用 |
| 3 | **真正的决策方在键盘/笔的充电 IC 与内核策略**；应用只能“回答宿主是否在充电” | `onGetChargingStateInqEvent` → `MbbHelper.sendChargingState(mHostChargingState)` |
| 4 | 该回答值的**语义是“宿主充电状态”，不是“笔电量”** | 同 3；`mHostChargingState` 来源为 `BatteryManager.isChargingEx()`（宿主的） |

> 换句话说：**“笔电量 90%”这个条件，在当前架构里没有任何一层会去看它来决定停充。**

## 4. 如果一定要实现“≥90% 停充”：三条路线与代价

| 路线 | 做法 | 前提/风险 |
|---|---|---|
| **A. root + 直接写 sysfs** | 轮询笔电量，≥90% 时向 `/sys/class/hw_power/charger/wireless_tx/tx_open` 写 `0`，低于阈值写 `1` | ❗ 需 root 且节点**可写**；完全绕过厂商充电策略，可能与键盘/霍尔状态机冲突，异常开关有安全与寿命风险；**节点在本版代码中未被引用，语义未确认** |
| **B. 改 APK（本笔包）** | 在 `onGetChargingStateInqEvent` 回发前插入判断：读 `honor_bt_pencil_battery_level` ≥90 则回发“宿主未充电”(0) | ❗ 需 root + 屏蔽签名校验（core patch/LSPosed）才能装回系统；语义副作用未知（键盘可能也据此改变自身行为/提示）；只能“间接”影响 |
| **C. 内核/固件层** | 在充电 IC 策略或键盘固件里加充电上限 | ❌ 普通用户不可行（正解但也最不可能） |

> 我的建议：**A 只在你能确认 sysfs 节点存在且可写、并接受风险时尝试；B 属于实验性质；C 放弃。**
> 更现实的做法是：不改充电，仅做“电量到达 90% 时提醒/让悬浮窗显示”这类**只读**的辅助功能（安全无害）。
