## 1. 方法论：这次真正管用的四个思路

### 1.1 区分「系统写的事实键」和「判定读取的键」

把所有键按"谁写"分类，是打开这个问题的钥匙：

| 键 | 写入者 | 是否参与悬浮球判定 | 可否伪造 |
|---|---|---|---|
| `honor_bt_pencil_connection_state` | 蓝牙包 | ✅ 第 6 条（需 != 0） | 可写，但会被事件覆盖 |
| `honor_bt_pencil_battery_level` | 蓝牙包 | ❌ | 无意义（纯显示） |
| `honor_bt_pencil_charging_state` | 蓝牙包 | **❌ 不参与** | — |
| `honor_stylus_wake_state` | 蓝牙包 | ❌（参考） | — |
| `honor_bt_pencil_model_number` | 蓝牙包 | ❌ | — |
| `key_bt_pencil_state` | floatmenu / 蓝牙包 | ✅ 需 ∈ {2,4} | **可写** |
| `key_pencil_attach_state` / `_type` | 蓝牙包 | ✅ 第 7 条（需非吸附） | **可写** |
| `stylus_support_floating_capsule` | 设置 UI | ✅ 第 1 条 | 可写 |
| `stylus_enable`（**System 表**） | 设置 UI | 疑似真开关 | 可写 |

**关键推论**：`honor_bt_pencil_charging_state` 由系统写、又不参与判定 →
它是唯一安全的**信号源**（见 §5 反相器方案）。

### 1.2 用「对照实验」找信号源，而不是猜

同一支 Magic-Pencil 3，只改变物理状态（取下 / 磁吸），读两次值：

| 键 | 取下 | 磁吸 |
|---|---|---|
| `honor_bt_pencil_charging_state` | **0** | **1** ★ |
| `key_pencil_attach_state` | 0 | 1 |
| `key_pencil_attach_type` | 1 | 1 |
| `key_bt_pencil_state` | 2 | 4 |
| `honor_bt_pencil_battery_level` | 79 | 80（充电中） |
| `honor_bt_pencil_connection_state` | 2 | 2 |

一次对照就把"哪个键反映磁吸"钉死了。比反复读 README 有用得多。

### 1.3 先验证「可伪造性」，再谈方案

不要先设计复杂方案，先用**一次最小写入**验证底层假设：

```bash
adb shell 'settings put global key_pencil_attach_state 0; sleep 2; \
           dumpsys window windows | grep -c FloatBallWindowView'
```

一条命令就能判定整套机制是否"只读 Settings"。这次实测窗口数 `0 → 6`，假设成立。

### 1.4 分清「UI 可骗」与「底层不可达」

这是整件事最重要的思维分界线：

```
Settings.Global  ← adb/Shizuku 能写
    ↓
floatmenu 的判定 p()  ← 只读 Settings → 可以骗，悬浮球能出来
    ↓
蓝牙包 onPencilConnected()  ← 需要真实 GATT 握手 → 骗不了
    ↓
AGPService stylus 场景（120Hz）  ← 需要 root/system → 完全够不着
```

**越往上越容易骗，越往下越硬。** 用户要的 120Hz 在最底层，所以注定拿不到。

## 2. 最重要的一条实测修正：这些键是「事件驱动」，不是周期轮询

我前几轮预判"系统会持续回写 `attach_state`，球会闪烁、必须高频 keepalive"——**这个判断错了**。

实测（磁吸状态下强行写 0）：

```
--- t+2s ---   key_pencil_attach_state=0   FloatBallWindowView=6
--- t+8s ---   key_pencil_attach_state=0   FloatBallWindowView=6   ← 纹丝不动
```

**推论**：系统只在"磁吸/取下"这类**物理事件发生的那一瞬间**写一次键，之后不再轮询覆盖。

**实践意义**（推翻了 README 第 11 节的悲观结论）：

- 一次写入**长期有效**，不需要 20 秒一轮的 `keepalive` 打地鼠；
- 伪造值会一直保持，直到下一次真实的插拔笔事件发生；
- 反相器方案的轮询间隔可以放到 30 秒甚至更长，开销几乎为零。

> 唯一仍然成立的障碍是：**谁来在每次插拔笔之后执行这次写入**（见 §5.3）。

> **⚠ 后续实测的修正（见 §10）**：`Settings` 里的值确实不会被系统覆盖，
> 但**悬浮球自身有 45 秒空闲超时**——笔长时间无输入，服务自己会把球收掉，
> 哪怕 `attach_state` 仍是 0。所以"长期有效"只对"键值"成立，对"球的可见性"不成立。
> 若要常显，重新触发的间隔必须 **< 30 秒**（留余量）。

## 3. 悬浮球判定：真机实测确认的三条

### 3.1 判定是 AND 关系，开关绕不过"吸附"这一条

实测：磁吸时即便把 `stylus_support_floating_capsule` 写成 1，球仍不出来。
因为第 7 条 `Pencil is Attached` 独立拦截。

**结论**：要实现"磁吸时显示"，**必须伪造 `key_pencil_attach_state`**，没有替代路径。

### 3.2 窗口存在 ≠ 可见，要看 `mViewVisibility`

第一次诊断时看到窗口 `alpha=0.0`、`oldVis=0 newVis=0`，那其实是**隐藏态**。
伪造成功后复查：

```
Requested w=152 h=152
mViewVisibility=0x0     ← View.VISIBLE
mObscured=false         ← 未被遮挡
```

**判定标准**：`dumpsys window windows | grep -c FloatBallWindowView` 得到非 0 只说明窗口建了，
要确认真显示必须看 `mViewVisibility`。

### 3.3 球的位置会被记住

```
key_stylus_ball_rect_left=3042  top=922  right=3189  bottom=1069
```

与窗口 frame `[3042,922][3194,1074]` 吻合。说明球曾正常显示过并持久化了位置。

## 4. 必须纠正的错误（静态分析 & 脚本的真实缺陷）

### 4.1 脚本查错了表 —— `stylus_support_floating_capsule = null` 是误报

脚本只查 `Settings.Global`，只读检查里报：

```
stylus_support_floating_capsule  = null   FAIL -> 总开关未开
```

但在 **`Settings.System`** 表里发现：

```
stylus_enable          = 1      ★
stylus_state_introduce = 1
```

而实测**在 `stylus_support_floating_capsule` 仍为 null 的情况下，悬浮球照样成功显示**。

**结论**：那个 `null` 不是卡点，脚本的 `v_switch` 判空逻辑是**误报**。
真正的开关很可能就是 System 表的 `stylus_enable`（已经是 1）。

> 教训：静态分析能确定"有哪些键"，但确定不了"哪个键在真机上真正生效"。
> 而且脚本**从没看过 System 表**，这是设计盲区。

### 4.2 `start_ball()` 是死代码（100% 失败）

`dumpsys activity services` 直接给出了铁证：

```
permission=com.hihonor.stylus.floatcapsule.STYLUS_MENU   ← 签名级权限
```

shell（adb / Shizuku）**永远**拿不到 `signature` 级权限，`am start-service` 必被拒。

另外服务本身其实**一直在正常运行**（`ServiceRecord` 存在，intent 带 extras），
根本不需要你去"拉起"它。

### 4.3 `fps scene-on` 也是死代码（三重失败）

```94:103:stylus_float_menu.sh
_scene() {
    if [ -n "$SU" ]; then
        su -c "service call AGPService 0x7a i32 $1"
```

三个独立问题，任一都会让它失败：

1. **需要 root/system** —— Shizuku 只有 shell，直接 `return 1`；
2. **`service call` 不写 interface token** —— 而源码是 `parcel.writeInterfaceToken("AGPService")`，
   参数对不上必然 transact 失败；
3. **事务码 `0x7a` 随固件版本变化** —— 换版本即失效。

### 4.4 README 教的"看日志定位第几道门"在这台机器上走不通

按 README 第 6 节抓 `StylusFloatingCapsuleService|BtPencilStateHelper|PencilController`，
**一条 app 判定日志都没打出来**（只匹配到 WindowManager 的窗口名）。

原因：荣耀对系统 app 的 debug 日志做了限流。

**后果**：`README` 第 6 节那张"九条判定 → 日志关键字"的排障表在这台设备上**不可用**，
必须改用"改 Settings + 看窗口"的黑盒验证法。

### 4.5 脚本里真正有价值的两个设计（应当保留）

- `trigger_detach()` 的 **1 → 0 跳变**：`ContentObserver` 只在值变化时回调，重复写同值无效。这个设计是对的。
- `backup` / `rollback`：实测可用，写值前务必先跑。

## 5. 可行的操作方案（全部经实测验证）

### 5.1 让悬浮球出现（已验证有效）

```bash
# 前提：key_bt_pencil_state 需为 2 或 4（CD52 未连接时是 0，要先写 2）
adb shell settings put global key_bt_pencil_state 2
adb shell settings put global key_pencil_attach_state 0
```

验证：

```bash
adb shell 'dumpsys window windows | grep -c FloatBallWindowView'   # 非 0 即出现
```

### 5.2 让悬浮球隐藏

```bash
adb shell 'settings put global key_pencil_attach_type 1; \
           settings put global key_pencil_attach_state 1'
```

### 5.3 「反相器」：磁吸=显示，取下=隐藏（技术可行，但需常驻）

**核心设计（这是本方案唯一正确的写法）**：

```
监听 honor_bt_pencil_charging_state（系统写，不参与判定）
        ↓
写   key_pencil_attach_state（参与判定）
```

单向、异键，**不会自触发震荡**。

反面教材：**绝对不要"监听 A 写 A"**。因为 `Settings.Global` 不记录写入者，
你写的 0 会立刻触发你自己的监听器，形成死循环：

```
系统写 1 → 你写 0 → 监听器看到 0 → 你写 1 → 看到 1 → 你写 0 → ……
```

而且无法用"值比较"破解：磁吸时系统写 1、你写 0；取下时系统写 0、你也写 0 ——
后者的"自己写的 0"和"系统写的 0"**区分不开**。

**真正剩下的唯一障碍是常驻执行环境**：

| 载体 | 结论 |
|---|---|
| 电脑跑 `while :; do adb shell ...; done` | 拔线即失效 |
| Shizuku + 终端 app 前台挂循环 | 后台会被杀 |
| Shizuku + Tasker/MacroDroid 定时轮询 | 可用，但**重启后 Shizuku 失效**，需重新激活 |
| root + Magisk 开机脚本 | 一劳永逸（用户当前无 root） |

由于 §2 证明了"事件驱动、一次写入长期有效"，轮询间隔可以放到 30 秒，
循环里只在值不匹配时才写，开销极小。

## 6. CD52（第一代 M-Pencil）死因完整分析

### 6.1 实测数据

```
honor_bt_pencil_connection_state = 1        （对比 Magic-Pencil 3 是 2）
key_bt_pencil_state              = 0        ← 状态机判定为"断开"
honor_bt_pencil_battery_level    = -1       ★ 蓝牙包读不到电量
honor_stylus_wake_state          = 1        ← 判定为"休眠"
honor_bt_pencil_model_number     = HONOR Magic-Pencil 3   ★ 还是上一支笔的残留
```

### 6.2 蓝牙层面：全都通了（硬件没问题）

`dumpsys bluetooth_manager`：

```
XX:XX:XX:XX:83:52  "M-Pencil"
  [ACL BR/EDR:N LE:Y]                      ← LE 链路已建立
  Encryption status LE: keySize=16         ← 已加密
  Packages: com.hihonor.hnbluetoothpencilmanager   ← 蓝牙包已接管该设备
  15:17:39  bond_state_changed → BONDED
  GATT_CH_OPEN, ACL holders: hnbluetoothpencilmanager(73), hid(49)   ★ HID 已持有链路
```

### 6.3 HID 层面：VID/PID 完全合规，但**没注册成笔**

```
249: M-Pencil Keyboard
  Classes: KEYBOARD | EXTERNAL            ★ 只有 KEYBOARD，没有 STYLUS
  Identifier: bus=0x0005, vendor=0x12d1, product=0x1091
  UniqueId: 70:61:ee:03:83:52

248: M-Pencil Mouse
  Identifier: bus=0x0005, vendor=0x12d1, product=0x1091
```

- `vendor=0x12d1` ✅ 白名单第一层要求的两个 VID 之一
- `product=0x1091` = 4241 ✅ 正是 `HnBlePeripheralCfgpencilpid` 列表的第一项

**白名单校验该过的都过了。** 但系统判定：

```
Stylus Fusion:
  ExternalStylusPresence: NONE            ★ 系统认定：当前没有外部手写笔
```

### 6.3.1 【重要修正】"没有 STYLUS 描述符"不是 CD52 的故障

后来在**华为平板 BAH3-W59 + 同一支 CD52**（MAC 同样是 `70:61:ee:03:83:52`）上做了对照：

```
7: M-Pencil
  Classes: 0x80000009        = EXTERNAL | CURSOR | KEYBOARD
  Identifier: bus=0x0005, vendor=0x12d1, product=0x1091, version=0x0000
```

**在原生环境里它同样没有 `STYLUS` class。** 差别只是华为合并成 1 个节点，荣耀拆成 2 个
（Keyboard + Mouse）——那是拆分方式不同，不是能力差异。

结论：**"无 STYLUS 描述符"是 CD52 自身的正常设计，不是故障，也不是荣耀造成的。**

真正承载笔迹的是屏幕触控通道，两边都存在且对称：

```
荣耀：honor,ts_pen
华为：huawei,ts_pen     DeviceType: touchScreen
```

所以笔迹从来不走 HID STYLUS，**这条必须从 CD52 的死因清单里划掉**。

### 6.4 结论：软件放弃支持，不是硬件不支持

判定依据是**反证法**——如果硬件不支持，链路应当断在最底层，但：

| 环节 | 结果 | 排除 |
|---|---|---|
| BLE 发现 / 配对 | ✅ BONDED | 排除无线硬件问题 |
| LE 加密 | ✅ keySize=16 | 排除协议栈问题 |
| HID 通道建立 | ✅ 建出节点 | 排除 HID 硬件问题 |
| HID 描述符无 STYLUS | ⚪ 华为上同样如此 | **不是故障**（见 §6.3.1，已从死因划掉） |
| **GATT 电量/型号读取** | ❌ `battery=-1`、型号残留 | **唯一死因：私有协议解析层** |

硬件链路 100% 通，断的是**上层协议解析**。

> **同一支笔在华为平板上的对照（决定性证据）**
> ```
> huawei_bt_pencil_connection_state = 2      ✅ 已接管（荣耀上是 1）
> huawei_bt_pencil_battery_level    = 11     ✅ 有电量（荣耀上是 -1）
> huawei_bt_pencil_model_number     = M-Pencil ✅ 型号正确（荣耀上残留）
> huawei_bt_pencil_hall_state       = "00"   ✅ 三态字符串，=取下
> ```
> **CD52 硬件完全正常，是荣耀软件不认它。**

**为什么老平板能写**：用户确认 CD52 在远古荣耀/华为平板上可写字。
这说明 CD52 的笔迹走的**不是标准 HID digitizer**，而是荣耀私有蓝牙协议——
由老固件的蓝牙包解析后注入为笔输入。新版 `hnbluetoothpencilmanager 11.0.0.7`
（Android 16）只保留了 Magic-Pencil 3 的新协议，把老协议实现拿掉了。

于是 CD52 退化成一个"会报按键的蓝牙键盘"：`249 Keyboard` + `248 Mouse` 两个节点是活的，
**笔身按键可能仍能当蓝牙键盘/鼠标使用，但笔迹输入没了**。

### 6.5 为什么救不回来

要让 CD52 写字，必须完整重建这套链路：GATT 抓包逆向私有协议 → 解析坐标/压力/倾角 →
注入 stylus 输入事件。这需要 `INJECT_EVENTS` 级能力 + 常驻服务 + 协议逆向，
**既不是改 Settings 能做到的，也不是 Shizuku 权限能覆盖的**；即便做成，延迟也无法书写。

> **adb、Shizuku、甚至 root 都救不回 CD52 的书写功能**（除非自行实现驱动级方案）。

### 6.6 已尝试且确认无效的干预

```bash
adb shell am force-stop com.hihonor.hnbluetoothpencilmanager   # 重启蓝牙包
```

重启后 `MainService` 正常恢复（8 处匹配），但 `battery=-1`、型号残留**完全没变** →
证明不是"状态机卡住需要重启"，而是协议层根本不匹配。

## 7. 120Hz 的真相（用户的原始诉求）

三层结构，只有最上一层可伪造：

| 层 | 控制方式 | adb/Shizuku 能否触及 |
|---|---|---|
| `min_refresh_rate` / `peak_refresh_rate`（System） | AOSP 约定键 | 可写，**但荣耀未必读它**，且会被"智能刷新率"覆盖 |
| floatmenu 悬浮球 UI | `Settings.Global` 判定 | **可伪造**（已实测成功） |
| AGPService stylus 场景（真正的高刷） | 蓝牙包真实事件驱动 | **够不着**，需 root/system |

**核心结论**：观察到的"悬浮菜单出现 → 120Hz"是**伴生关系，不是因果**。
两者都是"笔被蓝牙包判定为已连接/唤醒"的结果，各自独立触发。
伪造 Settings 只能骗出悬浮球，**骗不出 AGPService 的 stylus 场景**。

对 CD52 尤其绝望：它压根没被蓝牙包接管，连"笔唤醒"事件都发不出来，
AGPService 那条路连理论可能都没有。

**真正能拿到 120Hz 的做法**：
设置 → 显示和亮度 → 屏幕刷新率 → 选"高"，并关闭"智能/动态刷新率"。
（配合 Magic-Pencil 3 才完整。）

## 10. 第二轮实测：帧率 / 采样率的定量结论（推翻前版两处判断）

用 `手写笔帧率、触控率、刷新和悬浮菜单关联测试.sh` 的 `guide`（五阶段 2×2 + 复测，
每阶段前 12 秒冷却）与 `idle` 跑出来的真机数据。

### 10.1 五阶段实测结果

| 阶段 | 球 | 动作 | 刷新率 | 笔采样率 |
|---|---|---|---|---|
| 1 | 隐藏 | 静止 | **60 Hz** | — |
| 2 | 隐藏 | 画线 | **120 Hz** | 236.0 Hz |
| 3 | **显示** | 静止 | **120 Hz** | — |
| 4 | **显示** | 画线 | **120 Hz** | 236.4 Hz |
| 5 | 隐藏 | 静止（复测） | **120 Hz** | — |

### 10.2 结论：悬浮球对帧率与采样率**零影响**

**主判据必须是「阶段 3 vs 阶段 5」**——两者都处于"已画过线"的激活态，
唯一差别就是球在不在，是唯一干净的对照。结果 120 = 120。

> **⚠ 我第一版给的判读标准（1 vs 3）是错的。** 阶段 1 是"从未画过线"的待机态，
> 阶段 3 是"刚画过线"的激活态，两者差的不止是球——**激活历史不同属于混淆变量**。
> 拿 1 vs 3 对比会得出"球把帧率从 60 抬到 120"的错误结论。

### 10.3 直接回答了原始诉求：书写时本来就是 120Hz

用户的原始担忧是"没有悬浮菜单就只有 90Hz，写不进去"。实测否定：

- **待机（长时间不碰笔）= 60Hz**，这是唯一出现低帧率的状态；
- **一动笔画线立刻上 120Hz**，与球无关（阶段 2 球隐藏照样 120）；
- 笔采样率稳定 **约 236 Hz**。

所以"120Hz + 高触控采样"在书写时**本来就有**，不需要悬浮菜单，也不需要任何 adb 操作。

### 10.4 采样率测量的陷阱（务必注意）

第一轮曾测出 `150.8 vs 239.6` 的假差异，原因是阶段 2 的 **最大间隔 = 1.4035 秒**
——用户中途停了手，停顿把平均值拉低。

**判读规则**：对比采样率时必须同时看 `最大间隔`。若两者差距大而最大间隔也差很多，
那是画线节奏不同，不是被测变量的作用。第二轮两个阶段的采样率
`236.0 / 236.4` 几乎完全一致，才是可信结论。

### 10.5 悬浮球空闲超时 = 30~45 秒

```
t=30s  窗口数=6
t=45s  窗口数=0   ← 自行消失
```

比用户主观感觉的"几分钟"短。影响：

- `Settings` 键值不会被系统覆盖（§2 成立）；
- 但**球自身会超时消失**——哪怕 `attach_state` 仍是 0；
- 保活循环间隔必须 **< 30 秒**（45 秒是上限，留余量取 30）。

### 10.6 环境信息修正

- `ro.build.version.release = 17`（**Android 17**，不是 16）；
- 屏幕 `supportedRefreshRates [165, 144, 120, 90, 60, 48, 30]`，硬件最高 **165Hz**；
- 但 `frameRateCategoryRate {normal=60.0, high=90.0}` —— ROM 的"高刷档位"只定义到 **90Hz**；
- 笔迹输入走 **`/dev/input/event7 "honor,ts_pen"`**（不是 `M-Pencil Keyboard/Mouse` 那两个节点）；
- 笔休眠/磁吸时 `ts_pen` 完全不上报，测采样率前必须先让球显示。

### 10.7 方法论补充

1. **找干净对照**：两个待比较的状态，除了被测变量外，其他（尤其是"历史状态"）必须一致。
   这次踩的坑就是拿"待机态"和"激活态"对比。
2. **测量会干扰被测对象**：在手机上的终端 app 里跑倒计时，每秒刷新屏幕文字本身就会
   把刷新率顶上去，污染静止基线 → 必须用电脑 adb 跑。
3. **人机实验必须脚本主导节奏**：让用户自己判断"什么时候动"必然引入误差，
   应由脚本倒计时并明确告知"进行中/停手"。
4. **不要用 `kill` 杀 adb shell 里的后台子 shell**——会把整个会话一起杀掉
   （表现为只输出 `Terminated`，采样结果全丢）。改用"有限次数 + 自然结束"。

## 11. 最终机制模型与官方解法（用户实测观察补全）

用户补充的观察把整条链路完全闭合了，也**修正了 §10 结论的适用范围**。

### 11.1 用户的完整观察（可信，真机长期体感）

1. 荣耀笔记里，**只有悬浮快捷菜单出现后才能 120Hz**；
2. 笔连着但菜单消失时，**手碰一下 = 90Hz**；
3. **手一碰屏幕，笔会被自动唤醒并弹出悬浮菜单，随即变 120Hz**；
4. 上述现象发生在「智能刷新率」模式下；
5. 设置里还有 **「高刷新率管理」的按应用名单**——**把笔记加进去后，不管笔连不连都 120Hz**；
6. 不加进名单 → 手操作就是 90Hz；
7. **省电模式强制 60Hz**（优先级最高）。

### 11.2 双通道模型（最终版）

| | 触摸通道（手） | stylus 通道（笔唤醒） |
|---|---|---|
| 静止 / 低负载 | 60 | 60 |
| 书写 / 高负载 | **90** | **120** |
| 触控报点 | 跟着 vsync 走 | 独立全速（实测 236 Hz） |
| 激活条件 | 默认 | 蓝牙包判定笔「已连接/唤醒」 |

- `frameRateCategoryRate {normal=60.0, high=90.0}` 就是**触摸通道**的定义，"高"只到 90；
- stylus 通道是另一套策略（60/120），**不经过 normal/high**；
- 这解释了 §10 实测中"笔画线 = 120"与用户"手碰 = 90"并不矛盾——
  **决定通道的是「笔有没有被唤醒」，不是「用笔还是用手」**。

### 11.3 悬浮菜单的真实角色（重要修正）

§10 实测结论"球对帧率零影响"**只在笔正在书写时成立**（笔活动本身已经激活了
stylus 通道，球只是 UI，去掉它照样 120）。

但在「笔记 App + 手操作」的场景下：

- 手触摸**不会**激活 stylus 通道 → 走触摸通道 → 90Hz；
- 一旦笔被唤醒（悬浮菜单出现，即 stylus 通道激活的**可见标志**）→ 120Hz。

所以准确表述是：

> **悬浮菜单不是帧率的原因，而是「stylus 通道已激活」的指示灯。**
> 用户"卡蓝牙配对"能拿到 120，本质是**手动制造一次笔唤醒事件**来激活 stylus 通道，
> 球只是让它变得可见。

### 11.4 官方解法：按应用高刷名单（这就是正解）

**设置 → 显示和亮度 → 屏幕刷新率 → 高刷新率管理 → 添加「笔记」**

加进去后该 App **不管笔连不连都强制 120Hz**，等于绕开了"必须唤醒笔"的依赖。

这也顺带解决了 CD52 困境的另一半：即使某支笔无法激活 stylus 通道，
只要 App 在高刷名单里，依然能拿到 120Hz（但 CD52 本身书写功能已失效，见 §6）。

### 11.5 推荐配置（用户的最终设置）

1. 刷新率模式选 **「高」**（不要停在"智能"，也不要开省电）；
2. **高刷新率管理**里把笔记 App 加入名单；
3. 避开省电模式（它强制 60Hz，优先级最高）。

### 11.6 adb 层面的结论：这条路走不通

为找这个名单的存储位置，实测排除了三条路：

| 方法 | 结果 |
|---|---|
| `min_refresh_rate` / `peak_refresh_rate`（AOSP） | 写入成功但**无效**，荣耀不读 |
| `cmd display set-user-preferred-display-mode` | `SecurityException: Package android does not belong to 2000`（荣耀 `HnSettingsProvider` 归属校验） |
| `cmd display set-match-content-frame-rate-pref` | 可改（原值 1=ALWAYS），瞬时能到 120 但**不持久** |

且三张 Settings 表里**没有任何 per-app 帧率名单**（grep 过 refresh/rate/mode/frame/fps
及 notepad 均无果）。该名单存在于荣耀系统服务内部，**shell 读不到，需 root**。

→ **结论：这个配置只能通过系统设置 UI 操作，adb/Shizuku 无法代劳。**

### 11.7 真笔在线实测补充（磁吸态，Magic-Pencil 3）

实测原始数据：

```
honor_bt_pencil_connection_state = 2      key_pencil_attach_state       = 1
key_bt_pencil_state              = 2      key_pencil_attach_type        = 1
honor_bt_pencil_charging_state   = 1      honor_stylus_wake_state       = 2
honor_bt_pencil_battery_level    = 89     honor_bt_pencil_model_number  = HONOR Magic-Pencil 3

ExternalStylusPresence = NONE     ★
悬浮球窗口数           = 0        ★（磁吸按设计强制隐藏）
静止刷新率             = 120 Hz   ★
```

#### 修正一：`ExternalStylusPresence` 永远是 NONE，不能当判据

真笔好好连着、电量 89、型号正确，它**依然**是 `NONE`。说明荣耀的笔
**不走 Android 的"外部触控笔"框架**——笔迹走屏幕内置的 `honor,ts_pen` 通道。

判断"系统认不认笔"的正确判据只有这三项：

| 判据 | 认了 | 没认 |
|---|---|---|
| `honor_bt_pencil_connection_state` | **2** | 0（断开）/ 1（连上但未接管） |
| `honor_bt_pencil_battery_level` | 具体数值 | **-1** |
| `honor_bt_pencil_model_number` | 本笔型号 | 残留上一支笔 |

CD52 正是卡在这三项（1 / -1 / 残留）。

#### 修正二：`key_bt_pencil_state` 不是可靠的磁吸指示器

同样是磁吸，早前抓到过 `4`，这次却是 `2`。真正稳定反映磁吸的是
**`key_pencil_attach_state` + `honor_bt_pencil_charging_state`**（两者同时为 1）。

#### 修正三：球隐藏但帧率仍 120 —— 分离的决定性证据

磁吸时系统**按设计**把球强制隐藏（窗口数 0，非人为伪造），
而 stylus 通道依然激活 → **静止也维持 120 Hz**。

这比 §10 的 A/B 伪造实验更有力（那次球是伪造的，这次是系统自己关的）：
**悬浮球与帧率彻底分离，球只是 stylus 通道激活的指示灯。**

用户"卡蓝牙出菜单才 120"的体感，真相是同一时刻**笔被唤醒**激活了 stylus 通道，
球只是恰好让它变得可见。

#### 附带发现

- 笔**连接且唤醒**时，静止也维持 **120 Hz**（不降频，为保笔的响应性）；
- 笔**断开**时，静止才降到 **60 Hz**；
- 所以"静止=60"只在笔不在线时成立，不能一概而论。

#### 收尾

`match-content-frame-rate-pref` 已恢复为原始值 **1**（ALWAYS），未留下改动。
