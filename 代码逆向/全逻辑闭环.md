## 3. 三个决定性“卡点”

### 卡点 1：vid/pid + PID 白名单（决定“算不算荣耀笔”）
```
HID 连接 → getHidDeviceInfo(dev,0)=vid、getHidDeviceInfo(dev,1)=pid
   ├─ vid==0 或 pid==0                → 不做笔处理，只 250ms 重试一次
   ├─ HnBlePeripheralCfgpencilpid 为空 → 白名单失效（updateConfig 直接报 invalid config）
   └─ isHnPencilDevice(vid,pid)==false → 跳过
只有三者都过 → handleBlePeripheralHidStateChanged() / setHidDeviceInfo() → 笔包才“认笔”
```
白名单链路（唯一的可修改点，且无 root 就能改）：
```
蓝牙应用 saveConfig()  →  Settings.Global \"HnBlePeripheralCfgpencilpid\"
                                        ↓ 读取
笔包 MainService.updateConfig()  →  sPencilPidList  →  isHwPencilDevice(vid,pid)
```
已知换算：`CD52 = 0x1091 = 4241`、`ALITA = 0x10a5 = 4261`；CD54 / CD54S 需从日志取。

### 卡点 2：霍尔/磁吸（决定“取下笔能否触发一次判定”）
```
设备是否有 TYPE_HALL(0x10002) 节点？
   ├─ 没有 → registerForHallSensor() 直接 return（“no target sensor!”）→ 这条路不存在
   └─ 有   → HallListener: hall = values[0] & 0x34
              hall != 0 且笔包未启动 → bindService(hall, \"hallChange\") → 只拉起笔包服务
              （笔包 onHallChanged 只处理键盘：hallState & 0x4 == 0x4 → onHallAttached()）
```
> **重要**：手写笔的 `key_pencil_attach_state` / `_type` **不是这条路写的**，也不在这五个包里 —— 五个包都只“读”它。
> 【推断】写入方在 framework / system_server（HONOR 输入/侧边触控框架）。
> 这正好解释实测结论：该键**事件驱动、写一次长期有效**（真实写入方只在物理事件时写一次）。

### 卡点 3：`key_bt_pencil_state ∈ {2,4}`（决定“悬浮球显不显示”）
```
state=2 的来源：笔包 GATT 连接成功(onPencilConnected) 或 笔上报唤醒(onGetPencilStateEvent)
state=4 的来源：磁吸/空鼠等子状态映射（F1/a.a 内 state 11/12 → 3/4）
state=1/0 的来源：笔休眠 / 断开 → 立刻隐藏球
```
配合 `p()` 的九条判定（见 2.3），**任何一条不过，球就不出现**。

## 4. 帧率真相（回应“手写笔到底会不会触发 120fps”）

| 层 | 是否碰刷新率 | 证据 |
|---|---|---|
| `com.android.bluetooth` | **否** | `AGPService` 0 命中、`refreshRate` 0 命中 |
| `com.hihonor.hnbluetoothpencilmanager` | **是（唯一）** | `setStylusScenceFps(int)` → `AGPService` transact `0x7a` |
| `com.hihonor.stylus.floatmenu` | **否** | `setFrameRate` / `preferredRefreshRate` 0 命中；smali 里只有 RecyclerView 与 UI 灯效的 `refreshRate` 字段 |
| `featurelayer…stylus`（笔迹引擎） | **否（只读）** | `Display.getRefreshRate()` → `HnStrokeEstimateImpl.setRefreshRate(F)` 供预测 |
| `com.hihonor.globalwrite` | **否** | `setFrameRate` / `AGPService` 0 命中 |

**唯一通道**：
```java
setStylusScenceFps(fps):
    ServiceManager.getService(\"AGPService\") → writeInterfaceToken(\"AGPService\")
    → writeInt(fps) → transact(0x7a)
// 触发点仅 4 处
笔 GATT 连接成功 → 60 (0x3c)          ← 常量 LOW_REFRESH_FPS
笔上报“唤醒”    → 60  日志 \"refresh low fps\"
笔上报“休眠”    → 0   日志 \"refresh high fps\"（RESET_FPS，交还系统）
笔断开/服务收尾 → 0
```

**结论**
- 手写笔**会**触发刷新率场景切换，但**触发者是“笔连接/唤醒”这件事**，不是悬浮菜单、不是笔记应用；
- 你【实测】看到的“球出现 = 120Hz”，是**伴生关系**：两者同源于“笔被笔包判定为连接/唤醒”；
- 因此 **“让球出现” ≠ “拿到 120Hz”**。

### 4.1 为什么传的是 60，实测却是 120【实测修正】

`setStylusScenceFps()` 四个触发点传的值只有 **60 和 0**，但真机实测写字是 **120Hz**——这个落差必须解释，否则会误以为笔场景只有 60Hz。

【推断】**60 是 stylus 场景的“激活参数 / 帧率下限”（常量名 `LOW_REFRESH_FPS` 也印证）**，不是最终刷新率。场景激活后，系统在其内部策略里动态调整：

| 状态 | 实测刷新率 | 说明 |
|---|---|---|
| 笔连接且唤醒（stylus 场景激活）· 静止 | **60 Hz** | 下限 |
| 笔连接且唤醒 · 书写 | **120 Hz** | 按需拉满 |
| 笔断开 / 休眠（`setStylusScenceFps(0)`）· 静止 | 60 Hz | 交还系统 |
| 笔断开 · 手操作笔记 | **90 Hz** | 走触摸通道的 `high` 档 |

即：**60 = “打开门”，120 = “门里的实际上限”**。0 = 关门交还系统。

### 4.2 悬浮球与帧率无关的决定性证据【实测】

```
磁吸状态：
  FloatBallWindowView 窗口数 = 0      ← 系统按设计强制隐藏（非人为伪造）
  静止刷新率            = 120 Hz      ← 球没了，帧率照样在
```

球被系统自己关掉，帧率依然 120。这比 A/B 伪造实验更有力——**悬浮球与帧率彻底分离**。

### 4.3 拿 120Hz 的正确姿势【实测修正】

- ❌ `min_refresh_rate` / `peak_refresh_rate`：写入 120 后刷新率**纹丝不动**，荣耀不读（见 §7 手段 D）
- ❌ `cmd display set-user-preferred-display-mode`：`SecurityException: Package android does not belong to 2000`（荣耀 `HnSettingsProvider` 归属校验）
- ❌ `cmd display set-match-content-frame-rate-pref`：瞬时能到 120 但**不持久**
- ✅ **设置 → 显示和亮度 → 屏幕刷新率 → 高刷新率管理 → 加「笔记」**：唯一实测稳定生效
- 🟡 **补 PID 白名单让系统真认笔**（§7 手段 A）：理论上能让 stylus 场景自动激活，待验证

> 补充冷知识：本机屏幕硬件最高支持 **165Hz**，但 `frameRateCategoryRate {normal=60.0, high=90.0}`
> ——ROM 把触摸通道的“高刷档位”只定义到 **90Hz**。所以用手操作撞到 90 不是笔的问题，是档位定义。

### 4.4 华为平板的反面印证【实测】

在华为 BAH3-W59（CD52 的原生环境）上：

```
mDefaultPeakRefreshRate: 60.0
PRIORITY_USER_SETTING -> Vote{width=-1, height=-1, minRefreshRate=0.0, maxRefreshRate=60.0}
```

**屏幕最高只有 60Hz。**

→ 华为四包 `AGPService` 0 命中（见 `华为vs荣耀对比.md` §1）**不是功能遗漏，是根本没有可切换的档位**。
对比本机 CGA-W00 支持 `165/144/120/90/60/48/30`，才需要 `setStylusScenceFps()` 去做笔场景调度。

> **结论**：「笔 → 120Hz」= **高刷屏** + **荣耀私有调度**，两者缺一不可。
> 它不是手写笔的通用能力，所以在华为体系里根本不存在这个动作。

同一轮还顺带证明了 CD52 的清白（详见 §5.1 与 `华为vs荣耀对比.md` §10）：
在华为上它 `connection_state=2`、`battery=11`、`model_number=M-Pencil`、`hall_state="00"` —— **硬件 100% 正常**。

## 5. 三种笔的失败点定位

| 笔 | 现象 | 代码级定位 | 结论 |
|---|---|---|---|
| **Magic-Pencil 3** | 连上即自动出悬浮球、自动 120Hz | 路 A 全过（vid/pid + PID 白名单）→ `state=2` → `p()` 通过 | 全链路正常 |
| **CD54 / CD54S（华为 M-Pencil 2/3）** | 能配对、能写、设置里名字正确，**无悬浮菜单**；狂点配对可卡出 | 路 B（霍尔）能把笔包服务拉起 → 所以“能用”；但 **state 出不来 2**：路 A 卡在 `vid/pid==0` 或 **PID 不在 `HnBlePeripheralCfgpencilpid`** → 笔包不接管/不发状态 | **不是硬件不支持，是“没被认定为荣耀笔”** |
| **CD52（第一代）** | **能配对、能连上，但用不了**：BONDED ✅、LE ACL 已连接 ✅、HID 注册成功 ✅，VID/PID 还**完全合规**；但 `battery=-1`、型号永远是上一支笔的残留值、`ExternalStylusPresence: NONE` | 卡在 **GATT 应用层握手**：蓝牙/HID 两层与 MP3 **完全一样**，唯独握手失败 → 笔包不写 `connection_state=2` → 无笔迹输入、无法触发 stylus 场景 | **adb / Shizuku / root 都救不回书写**（握手在笔包进程内部；除非重建私有协议栈，而新版已移除老协议） |

> ⚠️ **【实测修正】** 原先写的"配不上 / `isPencilCreateBondRejectedByFoldScreen()` 拒绝 createBond"**在本机不成立**：
> 本机 `ro.build.characteristics=tablet`（非折叠屏），该分支根本不触发。实测 CD52 **配对成功**。
> 它的死因是**握手失败**，不是配对被拒。

## 6. 为什么“狂点配对/取消配对”能把球卡出来

```text
每次“断开→重连”都会产生一次 hidState == 0（HID 已连接）：
   handleHidConnectionStateChange → sendHidConnStateChangeBoradcast（发 HID 广播）
   handlePencilOrKeyboardHidStateChanged: if (state==0 && !mIsHwPencilControllerServiceStarted) bindService(...)
        → 每次都尝试 bind 一次笔包 MainService
其中某一次恰好使笔包完成 GATT 连接 → broadcastConnectionStateChanged(2)
        → startPencilBallService(2) → 悬浮菜单 t(2) → p() 通过 → 球出现
球出现后，除非再来 0/1/3 类事件（断开/休眠），否则不会自动消失 → 看起来被“卡住”了
```
**本质**：反复制造“HID 连接成功”的时机，提高命中“state=2”的概率。

## 7. 修复与自动化手段（按可行性）

| 手段 | 原理 | 需要 | 风险/局限 | 实测结论 |
|---|---|---|---|---|
| **A. 补 PID 白名单** ★首选·根本解 | 写 `HnBlePeripheralCfgpencilpid`（十进制逗号分隔），让 `isHwPencilDevice()` 通过 → 笔包**真正认笔** → 自动走 `onPencilConnected()` → **真 120Hz + 真悬浮菜单** | adb / Shizuku | 需确认四个 `HnBlePeripheralCfg*` 键都非空；改后需重启蓝牙进程或重启设备 | 🟡 待验证（需先拿到 CD54/CD54S 的 PID，见 §5.1） |
| **E. 高刷新率管理名单** ★实测唯一稳定有效 | 设置 → 显示和亮度 → 屏幕刷新率 → 高刷新率管理 → 加「笔记」；该 App **恒定 120Hz**，直接绕开"必须唤醒笔"的前置条件 | 无（系统设置 UI） | 按 App 生效，非全局 | ✅ **实测有效**：加进去后不管用笔还是用手、笔连不连醒不醒，恒定 120 |
| **B. 只动 Settings 让球出现** | 写 `key_bt_pencil_state=2` + 伪造“取下笔”（`key_pencil_attach_state/type` 走 1→0 跳变触发 ContentObserver） | adb / Shizuku | 只是骗过判定；**不带来 120Hz** | ✅ 有效（球确实出来），但只是 UI 层 |
| **C. 看门狗常驻** | 轮询“笔已连接 + 球不存在” → 自动补一刀 | Tasker/MacroDroid + Shizuku，或 root | 球有 **45 秒空闲超时**，轮询必须 **<30 秒**；值不变时 ContentObserver 不回调，须跳变 | ✅ 有效（配套脚本 `复刻真笔机制.sh`） |
| **D. `min/peak_refresh_rate` 120** | AOSP 标准键 | adb | — | ❌ **实测无效**：写入 120 后刷新率纹丝不动，**荣耀根本不读这两个键** |
| **F. root 下发 AGPService** | `service call AGPService 0x7a i32 60` | root | `service call` 不写 interface token；事务码随版本变 | 🔴 未验证，大概率失败 |

> ### ★ 为什么把「补白名单」列为首选
> B / C 都是在**骗最上层的 UI**（`Settings` → floatmenu 判定），球出来了，但 stylus 场景没激活，帧率纹丝不动。
> A 是让系统**真正认这支笔**：`isHwPencilDevice()` 一过，笔包就会自己走 `onPencilConnected()`
> → `setStylusScenceFps()` → **真的激活 stylus 场景**。这是根子上的解法，与伪造有本质区别。
>
> 操作模板（拿到 CD54/CD54S 后）：
> ```bash
> adb shell 'dumpsys input | grep -A14 -iE "pencil" | grep -iE "Identifier"'   # 取 vid/pid
> adb shell 'settings get global HnBlePeripheralCfgpencilpid'                  # 看现有白名单
> adb shell 'settings put global HnBlePeripheralCfgpencilpid "4241,4261,9473,9474,9475,9476,9477,9478,<新PID>"'
> adb shell 'am force-stop com.android.bluetooth'                              # 重启蓝牙进程
> ```

## 9. 仍未闭环（诚实标注）

1. **`key_pencil_attach_state` / `key_pencil_attach_type` 的写入方不在五个包内** —— 【推断】在 framework / system_server（这也解释了它“事件驱动、写一次长期有效”）。
2. `onHallChanged()` 只处理键盘（`&0x4`），**手写笔磁吸位被忽略**；那么“笔的吸附状态”到底由谁写，需要 framework 侧才能确认。
3. `handleBlePeripheralHidStateChanged()` 后 ~78 行（“认定后”的具体动作：是否再 bind、发什么）未读。
4. `sendHidConnStateChangeBoradcast()` 后 ~42 行（`sendBroadcastAsUser` 的权限名）未读。
5. `HallListener` 位掩码 `0x34` 各位的精确语义（笔吸附/笔取下/键盘吸附）未逐位确认。
6. 设备是否存在 `TYPE_HALL(0x10002)` 节点 —— 需真机 `getevent -pl` / logcat 确认。
7. CD54 / CD54S 的真实 PID —— 需从 `in handleHidConnectionStateChange vid=…, pid=…` 抓取。
